## Design and implementation

The existing host-controlled `MemoryStore` now owns two additional SQLite tables, `graph_entities` and `graph_relationships`. They index stable references to project, memory, TaskStore task, uploaded-file, and generated-artifact records; TaskStore and the existing memory tables remain authoritative. Graph rows contain typed identifiers, provenance, timestamps, and current/superseded/deleted state. Relationship types include `PROJECT_HAS_MEMORY`, `TASK_BELONGS_TO_PROJECT`, `TASK_USES_FILE`, `TASK_PRODUCES_ARTIFACT`, `TASK_CONTINUES_TASK`, `MEMORY_SUPERSEDES_MEMORY`, and `TASK_USES_MEMORY`.

The schema initializes transactionally and backfills existing project, memory, memory-reference, and project/task-context rows without changing those source records. The controller indexes its latest 100 TaskStore tasks at startup and synchronizes a task when task/upload/artifact paths handle it. Stable type-prefixed entity IDs and a unique source/type/target constraint make repeated synchronization idempotent. The graph stores metadata and references only; it does not copy full task prompts/results, uploaded bytes, generated file contents, or conversation transcripts.

Lexical token overlap selects up to eight matching seed entities from the newest 500 graph entities and considers at most 500 current memory-text candidates. Traversal defaults to depth two and 32 entities, and accepts at most depth three and 64 entities. Results include matched nodes, connected nodes, relationship records, and source IDs. Graph traversal follows only current relationships; superseded memory nodes may appear only when reached through `MEMORY_SUPERSEDES_MEMORY`. Forgetting removes the active content and marks its node and incident relationships deleted, so graph search cannot retrieve forgotten content. Task/file retention remains controlled by the existing TaskStore and attachment policies.

The Telegram controller handles four deterministic owner-only graph query forms for project files, tasks using a filename, latest matching analysis outputs, and memory supersession. The graph is not a model tool. Retrieval cannot run a worker operation, approve a task, or authorize any side effect. No general LLM-driven relationship extraction was added. Uploaded documents, web pages, and model output do not write trusted graph data.

## Performance and limitations

Retrieval is deterministic lexical matching followed by indexed relationship lookup, with fixed candidate, seed, depth, and node bounds. No production-scale latency benchmark was run; expected work is bounded by the 500-entity/500-memory candidate scan plus the capped traversal. Graph backfill on controller startup re-indexes existing memory rows and the latest 100 tasks; older tasks become indexed when an existing task path handles them or when a saved memory reference links them. Lexical search can miss paraphrases and records outside the candidate window. The graph is a navigational index, not an independent source of truth, and direct unauthorized-account live testing remains unavailable.
