## Scope and deployment

This checkpoint adds an explicitly requested visible-browser mode to the existing browser-only task profile. It does not add shell access, combine workspace and browser profiles, change the selected model, alter Softnet, reseal/reset the VM, or enable automatic dispatch. Each run still requires the existing owner `/run` approval. No inference or task execution was used to deploy or test the broker.

The protected worker preflight passed before deployment: Tart was running under the protected launcher; Softnet policy, DNS relay, guest DNS, OpenCode authentication metadata, execution helper, workspace profile, browser profile, and overall worker readiness were verified. The Telegram controller was restarted through its user LaunchAgent; its singleton state showed one active process. The controller-private task database could not be opened by the deployment process, so a fresh host-side audit of active/unresolved task rows was not available. The owner had previously reported all schedules complete or cancelled and no running tasks; no historical task was resubmitted. No VM shutdown or reset was performed.

Chrome for Testing 159.0.8154.6 ARM64 was installed in the Ubuntu guest at `/opt/toothless/visible-browser`. The exact reviewed archive was 207,644,679 bytes; it had 306 entries and 430,344,758 bytes of extracted files. The archive was fetched from Google's Chrome for Testing storage endpoint. The archive has no detached publisher signature; verification matched Google's published CRC32C (`/LRbng==`) and the published MD5 represented by the response ETag (`49eab16cb6711168a5980a3e538c372d`), and recorded SHA-256 `4a9ea5f9422e268fff9df19908365b6d1e92da154607d0f90c7138cf6c42ce38`. The installed browser binary SHA-256 is `3818624ec1ee6760b7b0bf852d9b8ca5e70e089e55feb4c74f7591aadb1a05db`; `chrome --version` reported `Google Chrome for Testing 159.0.8154.6`. This is integrity/version verification, not signed publisher provenance. No apt packages, FFmpeg archive, or extra Playwright package was installed. The existing Playwright 1.65.2 runtime was copied into a root-owned guest-only directory; its version was rechecked.

The broker is deployed inside the existing desktop systemd service's private mount namespace, where it shares display `:99`; it is not an externally reachable service. The `toothless-browser` group contains only `toothless-agent` and `toothless-desktop`. The broker uses `/run/toothless-desktop/visible-browser.sock`, mode `0660`, owned by the desktop identity and that group. The task authorization directory is root-owned, group-readable only by `toothless-browser`, mode `0750`; each authorization record is root-owned and mode `0640`, and binds the exact task ID, execution ID, browser profile, visible mode, and expiry. The broker exposes only `navigate`, `extract_text`, `click_link`, and `close_session`; it does not expose a TCP/CDP listener. It checks the browser installation manifest and binary hash before serving requests.

The desktop systemd unit retains `PrivateTmp=yes`, `ProtectHome=yes`, `ProtectSystem=strict`, `NoNewPrivileges`, `MemoryMax=1G`, `CPUQuota=150%`, and `TasksMax=128`. Its network policy retains the established private/reserved, link-local, metadata, and IPv6 denial rules; only the documented local DNS stubs are allowed. No limit or network policy was broadened for this deployment. Immediately after deployment, the desktop service was active with the broker socket present; Chrome was not running and no TCP listener on ports 9222/9223 existed. The service was subsequently started by the owner's Telegram Open Desktop action but failed the existing readiness probe; the controller stopped it after its bounded 10-second wait, leaving no viewer session. Temporary archive files were removed. Guest free disk space after installation was 11,751,624,704 bytes.

## Desktop readiness failure found after deployment

The owner reported that Telegram's Open Desktop action returned “The graphical desktop did not become ready. No viewer session was created.” Protected worker readiness remained fully true. A read-only pinned-worker status request confirmed the desktop was inactive after the controller's failure path. The bounded systemd journal showed that the fixed `toothless-desktop.service` did start, then was stopped by the controller; the Xvfb keyboard-map warnings were explicitly nonfatal. The cause was a permission-contract mismatch introduced by the approved broker deployment: `/run/toothless-desktop` must be mode `0750` and group-owned by `toothless-browser` so only the two reviewed identities can reach the Unix socket, while the older guest helper treated any group permission bit as unsafe and returned `available: false`. This was not a Softnet, DNS, Tart, or VM readiness failure.

The fixed guest helper now accepts only a real desktop-owned directory with the exact `toothless-browser` group and mode `0750`, plus a regular desktop-owned `Xauthority` file with mode `0600`; symlinks, other modes, and mismatched ownership fail closed. The screenshot path uses the same predicate. The updated helper was installed via `ops/worker/install-execution-agent.sh` over the existing pinned-key path after full worker readiness passed. No service or network policy was weakened. The new regression test covers the accepted ACL and rejects loose directory mode, readable Xauthority, and symlinked Xauthority. The updated focused suite passed 104 tests, Ruff, BasedPyright, shell syntax, and diff checks. After redeployment, the owner confirmed the desktop viewer opened, the visible browser showed the Example Domain page, and the owner-approved task succeeded with one execution and one Telegram delivery.
