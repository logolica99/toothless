## Implemented locally

- Added `ops/supabase/migrations/0001_toothless_web.sql` with projects, conversations, messages, agent runs/events, approval requests, and versioned project context. Database rows are the authoritative web application store; no SQLite fallback exists.
- Added the local host DSN config implementation: `~/.config/toothless/web-console.env`, directory 0700/file 0600, atomic write, TLS/schema verification before save, and explicit legacy Keychain migration that refuses to overwrite and leaves the original item. The controller now runs this code. A DSN value is present but currently fails strict format validation, so no database connection is established.
- Added Argon2id first-admin setup using a one-use `web_console` grant issued only from the authorized Telegram owner flow; one DB singleton and a transaction lock prevent a second admin. Normal login uses generic failures, a persistent 15-minute/five-attempt limit per normalized username, Secure/HttpOnly/SameSite cookies, server-side hashed sessions with 12-hour expiry, CSRF validation, login rotation, revocation/logout-all, and reauthenticated password rotation. The code path is local only; no admin user exists yet.
- The existing `web_console` one-use code remains as an owner-authorized fallback. The app initializes the `Toothless Blog` project only after verified DB setup. Messages are saved as notes and receive a durable status stating that no worker run started.
- Added `asyncpg` 0.32.0 and `argon2-cffi` 25.1.0 to `pyproject.toml` and `uv.lock`. The `/web` Telegram command remains unchanged and does not change `/run` semantics.
- No browser JavaScript receives a DB credential. Runtime DSN is stored in the protected host env file and is never passed to the Ubuntu worker. The administrative connection is not accepted by the application. Connection hostnames are limited to documented Supabase DB/pooler domains, and SSL hostname/certificate verification is enforced.

## Deliberate gates and remaining work

The UI reports Supabase disconnected until both reviewed migrations are authorized/applied, the restricted runtime login is created and granted membership, and its DSN is enrolled. Supabase currently recommends direct connections for persistent backends when IPv6 is available and shared-pooler session mode for IPv4-only backends; use the method supplied by the project dashboard. See [Supabase connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres).

Automatic low-risk run start is explicitly false in the app status and no web request dispatches a worker operation. This is intentional. Phase 09.1 requires the real OpenCode session contract, durable host/DB intent reconciliation, live DB foundation, and separate owner authorization before any dispatch policy can be enabled. Existing Telegram dispatch and approvals remain unchanged. No database migration, external account action, admin account creation, or Supabase credential enrollment occurred. Fresh `/web` login/setup acceptance remains outstanding.
