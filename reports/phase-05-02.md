## Implementation

- Reused the existing TaskStore, `OpenCodeTaskRunner`, root-owned worker helper, `WorkerInterface`, pinned-key SSH backend, host execution store, and Telegram `/run`/`/cancel` paths. A task still dispatches only after explicit owner `/run`; queued Phase 04 tasks are not auto-started, and uncertain executions are not resubmitted.
- Replaced the deny-all OpenCode profile with ordered deny-by-default rules. It allows `read`, `edit` (OpenCode write/patch), `glob`, `grep`, and `shell`; denies external-directory requests and all other actions; and explicitly denies common sudo/su/doas, apt/dpkg, service-control, mount, reboot, and shutdown commands. The exact model remains `opencode-go/glm-5.3`; only the `opencode-go` provider is allowed. Plugins, MCP, skills, and subagents remain denied, and updates are disabled.
- Added Ubuntu system user `toothless-agent` (UID 999; primary group only). It has no SSH key and is not a member of sudo, admin, adm, docker, or root groups. The root-owned runner refuses non-root invocation and always drops the OpenCode process to this account. `/etc/toothless/opencode.json`, the runner, and `/usr/local/bin/opencode` remain root-owned.
- Moved OpenCode’s writable workspace and guest-local credential store under `/home/toothless-agent`. The existing worker file API exposes the workspace as `opencode-task-workspace/`; this preserves the existing SSH file-transfer interface without making `/home/admin` or its prior authentication directories accessible to the model user.
- The runner checks OpenCode 2.3.0, the configuration SHA-256, exact model/provider, effective permissions, empty plugins/MCP, and disabled updates before inference. It uses `opencode run --standalone --archived --format json`, a 120-second inference timeout, a 1 MiB event-output cap, a 64 KiB event cap, a 48 KB answer cap, and a 12-step agent limit. Structured `tool_use` events are summarized as tool names only; arguments are not retained in the model response.
- Root/system package-manager elevation remains disabled. The Ubuntu image has Python 3.12.3 but no system pip; a temporary venv probe failed because `ensurepip` and `python3-venv` are absent. Installing that Ubuntu package would require a one-time operator-approved guest package operation; the model has no sudo or apt/dpkg access. No browser, Telegram document attachment delivery, model tool registration on macOS, automatic queued-task dispatch, or model-controlled privileged guest operation was added.

## Security boundaries and limitations

- OpenCode shell tools run as the guest `toothless-agent`, not on macOS. The guest account cannot use sudo and cannot read the prior admin-account credential store. No Mac OpenCode auth directory, SSH private key, Telegram token, host filesystem mount, or host credential was copied into Ubuntu.
- The new identity requires its own guest-local OpenCode Go login. A shell child runs as the same UID as OpenCode and can read that account’s provider credential. This is a guest trust-domain exposure, not a credential-isolation guarantee. Use only the authorized low-risk OpenCode account and never store host secrets in the guest.
- OpenCode’s file permissions and shell command scanner are application controls, not an OS sandbox for every possible shell program. The user’s ordinary guest filesystem/process/public-network authority remains available to shell commands. Existing Softnet host/LAN isolation remains external to the VM, but public internet egress and DNS-based exfiltration remain possible. Phase 05.2 did not repeat Phase 01 network fixtures.
- Telegram sends text results only. There is no document-send implementation. The generated files can be read from the guest over the existing authenticated worker file interface. No baseline was changed or sealed; after reset, reinstall the fixed worker helper and Phase 05.2 guest configuration, then authenticate the new guest identity again.
