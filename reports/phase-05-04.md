## Implementation

The Telegram controller handles supported document/photo messages only after the exact numeric owner and private-chat checks. Unauthorized updates are recorded and ignored before any `getFile` call. The controller requests Telegram file metadata, validates the relative API file path, downloads through the authenticated file endpoint with a hard 512 KiB streaming cap, checks the actual byte count, and never logs request URLs or exception text containing those URLs. A file caption becomes the queued task request; an empty caption receives a bounded generic request. The task update ID remains the deduplication key.

Supported uploads are PDF, TXT, CSV, JSON, PNG, JPG/JPEG, and ZIP. Names are reduced to safe basenames and allowlisted extensions. PDF/PNG/JPEG signatures, UTF-8 text, and JSON syntax are checked. ZIP contents are read in memory only; traversal, absolute/backslash paths, symlinks, encrypted/nested archives, duplicate flattened names, unsupported members, excessive depth, more than 12 combined archive/files, more than 2 MiB expanded data, a member above 512 KiB, and ratios above 100:1 are rejected. Host-side attachment bytes live in an owner-only directory with mode-0600 opaque files, a 50 MiB and 500-file total cap, and no Mac directory mount into Ubuntu.

TaskStore now persists the Telegram file ID, caption, original safe filename, MIME type, byte count, host receipt time, opaque storage key, and task association. `/run` remains the only execution authorization. The host copies attachments through the existing authenticated pinned-key worker interface to `opencode-task-workspace/inputs/<task_id>/`; host paths and Telegram file IDs are not put in the OpenCode prompt. The fixed guest helper writes these files as the SSH admin user with mode 0644 inside the access-controlled OpenCode workspace, because the helper cannot change file ownership after dropping root privilege. The model is told to treat uploads as untrusted data and save requested files under `opencode-task-workspace/exports/<task_id>/`. Attached tasks are rejected before dispatch if they classify to the separate browser-only profile; the browser profile is not combined with workspace shell access.

Successful workspace tasks that request file output return only supported direct files from that fixed guest export directory. Per-file size is capped at 1 MiB; delivery is capped at 10 files and 4 MiB total. Images use Telegram `sendPhoto`, other supported files use `sendDocument`. A host delivery intent is persisted before each request, then updated with status and the Telegram message ID. A transport interruption or interrupted controller send is `uncertain` and is not automatically retried after restart.

## Limits and security notes

The selected OpenCode model may receive attachment content through the existing explicitly approved inference path when it reads the staged file; uploaded contents are not sent to other external services by this feature. The rootless guest process can read the guest-local OpenCode credential, and guest public egress remains possible, both pre-existing trust limitations. Host attachment storage is bounded but retained for task recovery/audit until an operator removes it; no automatic age-based purge is implemented. On uncertain Telegram file-send outcomes, the host records `uncertain` and refuses automatic resend, so the owner may need to inspect Telegram manually. Shell tools and browser tools remain in separate profiles; attached tasks cannot use the browser profile. No unattended task dispatch, package-manager elevation, or arbitrary host execution is enabled.

The task remains terminal failed after timeout; the partial result is saved for `/task`, and one-shot file delivery records prevent duplicate sending. The live upload acknowledgment includes a bold confirmation and a code-formatted `/run` command. Active tasks now persist a concise status update and send it in Telegram once per minute while the worker still reports `running`; updates report elapsed time and absence of a result rather than inferred model activity. A live run of this progress notification remains NOT RUN.
