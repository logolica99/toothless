## Investigation

The local visible broker is a sequential blocking Unix-socket server. Its MCP helper is also a synchronous stdio loop, and Playwright's synchronous API is invoked from that blocking path. The inspected call path does not create or enter an asyncio event loop, and the broker accepts and processes one request at a time. The owner-relayed “sync API inside asyncio loop” exception therefore remains unconfirmed; it is not reproduced by current local code or retained sanitized host records.

A concrete stale-session weakness was present: `browser_mcp` stored the Playwright driver, browser, and page in module globals, but reused a page based only on `page.is_closed()`. It did not verify that the browser remained connected or that the page still belonged to the live context. The broker enforced one active task/execution identity, but a failed tool call did not invalidate that execution, so later calls in the same approved run could keep using the same module state. The exact historical Chromium failure cause cannot be recovered from the retained records. A target crash, context closure, runtime conflict, memory pressure, process limit, and sandbox failure are not asserted as the historical root cause.

The task outcome bug is confirmed in code. The guest event parser treated a non-error process exit with any event stream as `succeeded`; it did not use browser tool error state or agent step usage to determine whether the requested browser work had evidence of completion. The browser agents have a configured 12-step ceiling. TaskStore previously had no `incomplete` terminal status, so a final explanatory response could be saved and delivered as a successful task even when no page text was extracted.

## Changes implemented locally

- The synchronous Playwright runtime now rejects use from an active asyncio loop or a different thread, checks browser connectivity and page/context ownership before reuse, clears all dependent references before close, and fails closed instead of silently launching a replacement after stale state is found.
- The visible broker now invalidates a browser execution after a tool failure, closes its context, and rejects subsequent browser calls from that same execution. A different separately authorized execution can acquire a fresh runtime only after the previous session has been closed or invalidated. No CDP endpoint or retry was added.
- Broker failures return only bounded structured metadata: host-bound execution ID, tool, invocation sequence, fixed failure category, allowlisted exception class, elapsed milliseconds, session state, browser connection state, and best-effort browser-process liveness. Raw exception messages, URLs, page text, credentials, screenshots, and DOM are excluded. The task runner parses only this fixed marker from browser tool error events and the host revalidates the diagnostic allowlist before persistence.
- The runner records ordered event metadata, browser tool error counts, step-start count, and the configured 12-step limit without storing raw event bodies. The existing 65,536-byte event cap, 1 MiB total output cap, 48,000-character final answer bound, and 8,192-byte browser result cap remain unchanged.
- TaskStore now supports an `incomplete` terminal outcome. A response following a recorded browser tool failure or reaching the configured 12-step budget is retained as a partial result, marked incomplete, and delivered with an explicit “objective not verified” notice. Result delivery remains separately recorded. Duplicate dispatch remains blocked by the terminal state. Historical statuses and results are not migrated or rewritten.

## Step-ceiling analysis

Both reviewed agent profiles set `steps` to 12. The first all-category attempt returned partial header categories and owner-relayed that it reached the ceiling; its retained diagnostics do not include a reliable step count. The next attempt's 38-event sanitized record shows repeated navigation errors and no extraction tool. The local parser now records observed step-start count and marks the result incomplete when that count reaches the configured limit. The limit was not increased. The model's exhaustive taxonomy claim remains dependent on the task's requested coverage and available source evidence; successful navigation alone is not proof that every tag/category was enumerated.
