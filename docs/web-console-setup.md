# Toothless private web console

The Phase 09 console is mounted at `/memory/app/` inside the existing private Memory Explorer route. It does not add or change a Tailscale Serve route. The owner requests a one-use code with `/web`; codes are scoped separately from Memory Explorer and desktop grants, expire after ten minutes, and are invalidated by the controller's remote-session epoch. The browser receives a short-lived HttpOnly, SameSite=Strict cookie and a separate CSRF cookie. The controller validates the private origin and stores no Supabase credential in browser storage.

Deployment note: the env-file configuration, Argon2id administrator bootstrap, and password login are deployed in the current controller. The existing private Tailscale Serve route is unchanged. The database is not yet connected, so administrator setup and normal password login remain unavailable until both migrations and the restricted runtime DSN are configured.

Review both `ops/supabase/migrations/0001_toothless_web.sql` and `ops/supabase/migrations/0002_toothless_web_auth.sql`. Apply them in order only after owner authorization, to the intended Supabase project, using an administrative connection in the Supabase SQL editor. The first migration creates the non-login `toothless_web` privilege role, private schema, owner RLS policies, and app tables. The second adds the singleton administrator, hashed sessions, login throttles, and security audit records. Neither migration is run by the application.

After the migrations, create a dedicated database login with a new strong password, and grant only membership in `toothless_web`. The login must be non-superuser and have no RLS bypass. Do not use a Supabase service-role key or admin/migration credential as the application credential. In the deployed app, the owner enters the restricted login DSN into the authenticated connection form; the host verifies TLS, the complete schema, and the connection before atomically writing `TOOTHLESS_SUPABASE_DSN` into `~/.config/toothless/web-console.env` with mode `0600` in a mode `0700` directory. The trusted Mac controller-side app reads this file; browser JavaScript and Ubuntu never receive the DSN. The administrative DSN is not accepted by the app. An explicit “Migrate existing Keychain connection” action copies the legacy `com.toothless.supabase` item only after verification and only if the env file does not already exist; it does not delete the old Keychain item. Rotate the login role at Supabase and remove the env file during credential retirement.

Once the database is connected, request an owner-only `/web` code in Telegram, open `/memory/app/setup`, and enter that one-use code together with the application username and password you choose. The code is consumed once; a database singleton constraint and transaction prevent a second admin from being created. `root` is allowed only as an application username and has no operating-system privileges. Later access uses the username/password login. Passwords are Argon2id-hashed in the private Supabase auth table and never written to the DSN file. Existing `/web` one-use login remains a documented owner-authorized fallback. Keep this setup URL private to the tailnet; the app does not offer public signup or password reset.

For a persistent Mac backend, Supabase currently recommends a direct database connection where IPv6 is available, and the shared pooler in session mode for IPv4-only networks. Use the connection method and endpoint supplied by the Supabase dashboard; do not compose a pooler hostname or choose transaction pooling for this long-running process. The backend limits its pool to three connections and applies bounded command/connect timeouts. See [Supabase's connection-method guidance](https://supabase.com/docs/guides/database/connecting-to-postgres).

The web store is an optional dependency of the managed Memory Explorer process. If the protected config file, driver, database, or migration is unavailable, the console reports storage unavailable and does not fall back to SQLite or start agent work. Web messages, when the database is connected, are durable notes with idempotency keys and an explicit persisted status message that no execution started. Telegram `/run` remains unchanged. Application owner authentication is provided by the server-side password session; the transaction-local RLS owner setting is not treated as independent authentication.

## Agent orchestration gate

The console does not run OpenCode. Message persistence is not execution. Automatic low-risk start is hard-coded off, and the UI says so. Do not enable it until the installed Ubuntu OpenCode version/session API is inspected, a durable run/approval/reconciliation implementation is reviewed, and the owner explicitly approves the precise authorization scope. Existing host TaskStore and execution/approval records remain authoritative; Supabase records are not worker authorization.
