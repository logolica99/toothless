# Telegram file security

## File flow

Only the configured numeric owner in a private Telegram chat can submit files. The controller checks that identity and chat before calling Telegram `getFile` or downloading bytes. It accepts PDF, TXT, CSV, JSON, PNG, JPG/JPEG, and small ZIP documents. A document upload creates one queued task; a caption becomes the task request, while an empty caption gets a generic review request. File upload does not authorize execution. The owner must send `/run <task_id>`.

Each downloaded file is limited to 512 KiB. The filename is reduced to a safe basename and an allowlisted extension. PNG/JPEG/PDF signatures are checked; text files must decode as UTF-8 and JSON must parse. A ZIP is screened and read in memory: at most 12 total files including the archive, 2 MiB expanded content, 512 KiB per member, 100:1 compression ratio, five path components, and no absolute or parent paths, backslashes, symlinks, encryption, duplicate flattened names, nested ZIPs, or unsupported file types. The Mac never extracts an uploaded path to disk.

Host metadata is stored in the existing private TaskStore database and includes Telegram file ID, caption, safe filename, MIME type, byte size, host receipt time, and task association. Opaque file bytes are stored under an owner-only `attachments/` directory beside the task database; each file is mode 0600. That directory has a hard 50 MiB / 500-file quota. The implementation fails closed at quota; it does not automatically delete source files by age. Operators may remove retained attachment files only when the corresponding tasks no longer need to be rerun or audited.

The host transfers attachments through the existing authenticated, pinned-key worker file interface only after `/run`. Guest files are placed under `opencode-task-workspace/inputs/<task_id>/` with mode 0644 so the rootless `toothless-agent` process can read them. The helper runs as the SSH admin identity for file operations and cannot change file ownership; staged files therefore remain admin-owned. The workspace's parent directory restricts traversal to the model identity and the trusted admin account. Attachment tasks have a fixed 300-second OpenCode deadline and 315-second worker deadline; ordinary workspace tasks retain 120/150 seconds and browser tasks retain 300/315 seconds. While the worker reports `running`, the controller persists and sends an elapsed-time status update once per minute without exposing model reasoning or claiming unseen progress. Upload contents are untrusted data and may be supplied to `opencode-go/glm-5.3` through the explicitly approved model-processing path. The same guest identity can read its guest-local provider credential; that pre-existing guest trust limitation remains.

## Output delivery

Workspace tasks are instructed to save owner-requested outputs under `opencode-task-workspace/exports/<task_id>/`. The controller only lists that task-specific directory, accepts direct regular files with PDF, TXT, CSV, JSON, PNG, or JPG/JPEG extensions, checks reported and actual lengths, and caps each file at 1 MiB, ten files, and 4 MiB total per task. Images use Telegram `sendPhoto`; other files use `sendDocument`. Host TaskStore records each send intent before the request and persists its status and Telegram message ID. A transport interruption is `uncertain`; it is never automatically resent after restart because Telegram may already have accepted the upload. A definite API rejection is `failed`. `/task <task_id>` displays stored file delivery status.

Task attachments cannot be dispatched through the browser-only profile. The host rejects that combination before claiming the task, and the OpenCode runner has a second profile guard. Workspace shell tools remain guest-only, rootless, and package-manager/system privilege denied. Generated guest files are never used as arbitrary host paths; the only bytes sent back to Telegram are read from the fixed task export directory through the worker interface.

## Verification state

Deterministic tests cover owner authorization before download, upload size and file validation, ZIP traversal and compression limits, durable host attachment associations, guest-only staging, output allowlisting, one-shot delivery records, and the existing worker cancellation/no-host-fallback contracts. The current live acceptance gate requires an owner-uploaded CSV, explicit `/run`, actual OpenCode computation, independently checked statistics, PNG and summary CSV delivery, restart recovery, and duplicate-run protection. Local mocks are not evidence of Telegram or guest execution. See [`../reports/phase-05-04.md`](../reports/phase-05-04.md).
